**In one line:** every existing screen is mapped to one of three reference archetypes, the places where the reference chrome cannot hold the real data are listed with a resolution each, and the conversion order is chosen so the shared chrome is proven on the highest-value screen first.

- **(A) framed dashboard** — header chips + nav rail + illustrated scene + right sidebar + bottom card strip (Concepts 1 and 3).
- **(B) focused combat view** — Concept 2.

## 3. Per-screen sections

Conventions for §3: "route" is the `res://game/screens/*.tscn` path and how it is reached (`goto` replaces the stack, `push` layers). All screens follow the same skeleton — `_ready()→build()` (idempotent, `_built` flag), `Services.router(self)` / `Services.state(self)` lookups, `Widgets.ground()` full-rect `ColorRect`, then `Widgets.page(margin)` → `Widgets.column(gap)` — so "structure" below lists only what differs. Every `.tscn` is a one-node shell (`Control` + script); nothing is laid out in the editor.

### 3.1 Town

- **File / route:** `game/screens/Town.gd` (207 lines), `Town.tscn`. Reached by `goto` from MainMenu "New Guild"/"Continue" and from every building's "Back to town". Root of the in-game stack; buildings are `push`ed on top.

- **Current structure:** ground → `page(32)` → `ScrollContainer` (v only) → `column(14)`: `_desk_strip()` (HBox, min-h 56) · rule · title "The Town" · meta tagline · rule · 5 × `_building_row` (column(2): HBox[ Button "Name — Verb" min-w 340 left-aligned, meta blurb ] + faint reason when locked) · rule · HBox[ Button "Back to menu" ].

- **Controls:** 5 building buttons (`push(scene)`; disabled with reason), "Back to menu" (`goto(MAIN_MENU)`).
- **Target:** **(A)** Concept 3 verbatim. Header chips ← desk strip (00 §2.5 maps the four chips; the pip meter becomes the rank-name text on chip 4 — the tooltip's "N more to <rank>" belongs on the chip tooltip). Nav rail ← `BUILDINGS` (00 §2.6: rail items are Town/Tavern/Roster/Market/Adventure's Board/Records/Settings; Blacksmith is a scene callout, not a rail item). ## 5. Test constraints

**How the tests read a screen.** Every UI test uses the same walker: recurse the mounted screen's subtree, collect `Label.text` and `Button.text` **only** (`test_screens.gd:_texts`, copied verbatim into `test_full_loop._all_text`, `test_raid_plan._texts`, `test_rest._texts`, `test_starting_roster._texts`, and `_labels`/`_printed` in `test_market`, `test_tavern`, `test_raider_detail`, `test_comfort`, `test_settings`). Button *pressing* is by text fragment: `_button_named(view, fragment)` (market/tavern/detail/comfort) returns the first `Button` whose `text.contains(fragment)`; `test_full_loop._press(text)` presses the first **enabled** button containing `text`. Nothing depends on node paths, node names, or container types — except `Widgets.button_of()` which looks up the child named `"Button"`.

Consequences for the rewrite:
1. Every asserted string must live in a `Label` or `Button`. `RichTextLabel`, `TextureRect`, `_draw()`, `Tree`, `ItemList` are invisible to the tests. A pixel-font `Label` is fine.
2. Buttons that tests press must stay `Button` (or a subclass — `TextureButton` is *not* a `Button` subclass; a styled `Button` with a `StyleBoxTexture` is).
3. `Button.text` must contain the fragment; icon-only buttons need the text kept (it may be made invisible via an empty-font override but must not be removed — safer: keep visible text).
