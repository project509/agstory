# 00-plan — waves 6-10: the ship plan for A Guild Story

Synthesised 2026-09-15 (during wave 5, read-only on the tree at HEAD 106ac8d) from the seven ship reports (SIM, CONTENT, LOOP, UI, AUDIO, SHIP, DESIGNER) and CRITIC. CRITIC's "Order and capacity" is the spine; where a report's wave column and CRITIC disagree, CRITIC wins and the unit says so; where CRITIC's own tables gave one file to two units in a wave (RaidView.gd and GameState.gd in wave 7, RaidView.gd and AdventureBoard.gd in wave 8, SceneStage.gd and RaidSim.gd in wave 9) this plan moves the work so every file has one owner per wave and says where it moved. Nothing in this plan changes a canon number (docs/_source is canon) or weakens a canon-guard test; every ambiguity the designer has not ruled lands behind a switch with the recommended default and is listed once in §6.

After wave 10 the game is shippable in this sense: a player installs the zip on a second machine, starts a guild, is taught by two tutorials that can be won, climbs a Tier 1 ladder that can be completed, reads a wipe report that names why, hears the stamp, and reaches an ending — with no sentence on any screen about a build, a module, a doc or an audit; every sprite, line and control showing as well as the shipped assets allow; and every unanswered designer question taken at a stated default in writing.

## 0. How to read this plan, and the rules every unit obeys

### 0.1 Inherit `build/plan/artaudit/00-plan.md` §0 by reference
Everything in that §0 stands: a unit is one agent, one commit series, one goal (§0.1); no two units in one wave own the same file, hot files have exactly one owner per wave, a needed edit in an unowned file is a `build/plan/handoff-<key>.md` the orchestrator applies between waves, a unit references only what exists at the wave's start or what it creates, string-named theme variations and dictionary keys fall back harmlessly so may be named a wave early, PNG paths and functions may not (§0.2); the shot grammar (§0.3, plus W5-TOOLS's `--hover=x,y` and the fourteen sheets); green and how a wave ends (§0.4); the contracts no unit may break (§0.5: `Label.text`/`Button.text` are the test surface, `Nav_*` order, `Widgets.tween` + `motion_duration`, the wipe members, the SceneStage names, `lint_motion.sh` text, `a11y_smoke.SCREENS`); the switch register (§0.6, now spec 00 §2.7). Write the report file first and append as you go — the two recon runs this project lost to usage limits are the reason (memory: parallel-agent-waves).

- **Brief reviews** (user rule 2026-09-14, memory: brief-reviews): one look that the new thing shows on its shot, its own test green, move on. No acceptance audits, no repair loops. Every unit's "Shot" line names the ONE picture the reviewer looks at.

### 0.4 Capacity and the shape of a wave
Wave 5 ran seven units in a day under the brief-review rule; five waves is ~35 units. Sizes are agent-afternoons: S = an hour or two, M = an afternoon, L = a long day that one session can still hold (write-as-you-go). No XL: every XL the reports proposed is split across waves or below the cut line (§7). Wave 6 is the heaviest by design (the designer's copy directive plus CRITIC's "nothing lies" — 7 units, three of them L) and wave 10 the lightest (a release wave needs slack). A unit whose acceptance needs another unit's new function in the same wave is a bug; where two units meet at a wave's close (wave 8's lever and price change; wave 9's kits and tier rows) the plan says which orchestrator step joins them.
