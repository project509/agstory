## Summary

The pipeline is real but narrow: lib.lua draws rounded/chamfered panels, gradients, glows and 9-slices, and four generators produce the chrome (7 nine-slices + 1 bubble), 28 gear icons, ~32 UI glyphs, 3 fire strips, 2 wipe textures. Every asset class the combat directive needs — damage numbers, hit/slash/bolt/heal strips, a boss at battle scale, combat-scale bodies, state glyphs — is absent, and the primitives to author them (line, ellipse, polygon, PNG import, real frames/tags) are not in lib.lua; gen_items.lua and gen_icons.lua each carry private copies. The sliced library is large (730 PNGs; 280 raider frames, 139 enemies, 56 VFX stills, 19 bosses) but every VFX and boss is a single still and the largest boss is 259x154. The bubble is one 33x32 sprite with one tail and no glyph vocabulary; callouts have no icon or pointer; nine class glyphs are 1/9; ~30 shipping icons are hand crops with no generator or manifest rect. Pipeline hygiene: build_art.sh never runs gen_icons.lua, nothing checks generated art against its generator, build/atlas is exported for no consumer, and docs/12 §7 describes a tree, manifest and filter rule that do not match the repo. pixel-mcp's 49 tools all have CLI/Lua equivalents except the analysis bin; the protocol in Part 3.4 keeps MCP out of the build. Sixteen findings: 3 P0 (damage numbers, VFX strips, boss scale), 6 P1, 5 P2, 2 P3; seven need a designer ruling, listed under Open questions.

## Part 1 — Inventory: what the pipeline generates today

### 1.1 lib.lua (tools/aseprite/lib.lua, 326 lines) — the whole primitive API
- Colour: `hex`, `rgba`, `chan`, `mix` (linear blend), `over` (source-over composite) — lib.lua:20-59.
- Pixels: `px` (replace, bounds-checked), `blend` (alpha-correct), `fill`, `fill_blend`, `grad` (vertical default, `horizontal=true`) — lib.lua:63-96.
- Rounded shapes: `rr_inside`, `rrect_fill`, `rrect_grad`, `rrect_border(inset)`, `rrect_glow(spread,a0)`, `notch` (45° corner cut with lit edge) — lib.lua:102-178.
- Chamfered shapes (the kit's real corner language, 06): `ch_inside`, `chrect_fill`, `chrect_grad(horizontal, which)`, `chrect_border(inset, which, sides)`, `rivet` — lib.lua:185-248.
- Composites: `panel(opts)` (glow+grad+inner+border), `inset(opts)` (well with bottom lip) — lib.lua:255-279.
- 9-slice: `add_nine_slice(spr,name,l,t,r,b)` (Aseprite slice with `center`), `check_nine_slice` (margin assert) — lib.lua:286-297.
- IO: `new_sprite(w,h)` (RGB, cleared), `img(spr)` (frame 1 cel only), `save_png` (saveCopyAs), `save_ase` (saveAs) — lib.lua:301-324.
- **What lib.lua cannot do** (relevant to the missing classes below): no line/circle/ellipse/polygon primitive, no text/glyph rendering, no multi-frame or tag helper (`img()` is frame 1 only; `new_sprite` has one frame), no layer helper, no diagonal/triangle fill beyond `notch`, no dither/noise, no radial gradient, no import-of-PNG helper (a generator cannot composite a sliced reference sprite), no palette lock. Every VFX strip, tail variant and glyph class therefore needs new primitives or a different route.

### 1.3 tools/build_art.sh (74 lines)
`--gen` runs every tools/aseprite/gen_*.lua through `$ASEPRITE -b --script` (build_art.sh:28-40). Then every art/**/*.aseprite is exported to build/atlas/<sub>/<name>.png + .json with `--sheet-type packed --list-tags --list-layers --trim` (build_art.sh:56-64). Note: the generators write game/assets/** PNGs DIRECTLY (gen_ui.lua:19); build/atlas is a disposable second export that the game does not load (see Part 4). `--trim` on the atlas export means the atlas frames are not the same size as the game PNGs — nothing consumes the atlas JSON today.


### 1.4 gen_fire.lua (142 lines) — the only animated strips in the pipeline
- Deterministic LCG-seeded flame painter (gen_fire.lua:24-74); `strip(name,w,h,frames,seed,scale,tongues)` paints ONE ROW of frames (gen_fire.lua:79-104). Frame width is implicit: the PNG is `w*frames` wide and the consumer must know `w` (see Part 4 for how SceneStage declares it).
- Outputs (art/src/vfx/*.aseprite + game/assets/vfx/*.png): fire_hearth 64x56x8 (512x56), fire_camp 40x52x8 (320x52), fire_torch 16x24x6 (96x24), ember 4x4, light_soft 64x64 radial alpha (gen_fire.lua:107-140). Measured on disk: game/assets/vfx = ember(4x4), fire_camp(320x52), fire_hearth(512x56), fire_torch(96x24), light_soft(64x64) — nothing else. There is NO hit spark, slash, bolt, heal sparkle, dust, or smoke strip anywhere under game/assets/vfx.
- The strip is saved as a single-frame sprite (`L.new_sprite` → 1 frame) with frames laid side by side in one cel, so the .aseprite carries NO frame tags or durations; docs/12 §7.3's "tags are the export contract" is not what the shipping strips do.

### 3.3 Tools that would be BUILD-VIOLATING if depended on
Any MCP call inside tools/build_art.sh, tools/verify.sh or a generator. The catalogue offers nothing the CLI cannot do; the only MCP-unique value is the analysis bin (3.1), which produces decisions, not files the build needs.

### 3.4 Recommended session protocol (so MCP output never becomes an unreproducible asset)
1. Design in MCP on a scratch .aseprite under the scratchpad, never under art/src.
2. When it looks right, `get_pixels` / `get_palette` to read the result, then write the generator (Lua spans or shapes) that reproduces it, and commit ONLY the generator + its outputs.
3. If the shape is too organic to code (a boss, an aerial figure), the .aseprite itself becomes the source under art/src/<class>/ and build_art.sh's export loop covers it — but then it must be hand-editable (real layers, frames, tags), not a flat one-cel dump.

## Part 4 — Integration conventions for adding an asset (as the tree actually works today)

1. **Source of truth**: an `.aseprite` under `art/src/<ui|items|vfx|…>/<name>.aseprite`, written by the generator via `L.save_ase` (lib.lua:319). docs/12 §7.1's tree (`art/characters/`, `art/gear/`, `art/fx/`…) is PROPOSED and NOT what exists; the real tree is `art/src/{ui,ui/icons,items,vfx}` plus the PIL-sliced library under `art/export/<category>/`. New classes should follow the real tree (e.g. `art/src/vfx/`, `art/src/ui/bubbles/`, `art/src/actors/`) and docs/12 §7.1 should be corrected (PIPE-13).
2. **Runtime PNG**: the generator writes the game file DIRECTLY — `game/assets/ui/<name>.png`, `game/assets/ui/icons/<name>.png`, `game/assets/vfx/<name>.png`, `game/assets/actors/<name>.png` (gen_ui.lua:19, gen_fire.lua:14, gen_icons.lua:22, gen_actors.py). `build/atlas/` is a SECOND export nothing loads (build_art.sh:56-64; no `build/atlas` reference exists in game/).
3. **.import file**: Godot writes `<name>.png.import` on first editor/headless import; the project default (215 files) is `compress/mode=0`, `mipmaps/generate=false`, `process/fix_alpha_border=true`. Commit the .import beside the PNG. Do not hand-write uids.
4. **Filtering**: project-wide `default_texture_filter=1` (LINEAR) is deliberate (project.godot:139-142, spec 11 §2). Sprites that must be crisp opt in per node: `texture_filter = CanvasItem.TEXTURE_FILTER_NEAREST` (SceneStage.gd:220/276/472/519, RaidView.gd:701). A new sprite class (damage glyphs, sparks, bubbles as Sprite2D) must set NEAREST on its node; UI TextureRects in the kit inherit LINEAR, which at 1:1 is identical. docs/12 §7.7 ("Nearest filter… bilinear anywhere destroys the look") contradicts the recorded ruling and should cite spec 11 §2 instead.
5. **Strips**: one row of frames, left to right. `frame_w` is declared by the CONSUMER, not the file: props in `game/assets/scenes/<scene>.json` carry `{"strip": path, "frame_w": N, "fps": F}` (SceneStage.gd:20, :454-459); actors carry `frame_w/frame_h/frames/fps` in `game/assets/actors/actors.json` (written by tools/art/gen_actors.py). `_strip_frames()` (SceneStage.gd:119-132) cuts every `frame_w` px; default is `tex.get_height()` (square frames). No JSON sidecar comes from Aseprite for these — the .aseprite has ONE frame with the strip drawn across it (gen_fire.lua:80). A new strip class should either (a) follow this and declare `frame_w` where it is consumed, or (b) author real frames and let build_art.sh's `--data` JSON drive it — but nothing reads that JSON today, so (a) is the zero-plumbing route.
6. **9-slices**: `L.add_nine_slice(spr, name, l,t,r,b)` stores the centre as an Aseprite slice (lib.lua:286); the margins are RE-DECLARED by hand in game/ui/Theme.gd's StyleBoxTexture (the JSON is not read). Keep both in sync; `L.check_nine_slice` asserts sanity at gen time.
7. **Regeneration**: `./tools/build_art.sh --gen` runs `tools/aseprite/gen_*.lua` only (build_art.sh:28-40). `tools/art/gen_icons.lua` and every tools/art/*.py generator must be run by hand. Deterministic output is a project rule (gen_fire.lua:10-11, gen_wipe.lua:20-24): no `math.random`, seeded LCGs only, so a re-run is byte-identical.
8. **Staleness gate**: tools/verify.sh stage 2/8 (verify.sh:85-110) checks only `tools/gen_items.gd -- check` (item DATA). There is NO check that a generated PNG matches its generator; gen_wipe.lua:20's "staleness manifest" does not exist. Add a `--check` mode to build_art.sh (regenerate into a temp dir, `cmp` against game/assets) and a stage 2b in verify.sh (PIPE-11).
9. **Tests**: assets are asserted by existence (`ResourceLoader.exists`) in tests/unit/test_screens.gd style, and screen content by `Label.text` / `Button.text` — so any new visual that carries words (damage number, callout) must remain a Label/Button node; a11y_smoke.gd needs keyboard focus on interactive plates; `tools/lint_motion.sh` requires every `create_tween()` to sit behind a `reduced_motion` check.
10. **Slicing from the reference sheets**: `python tools/art/slice.py islands <sheet> --key alpha|white|dark --thresh N --region x,y,w,h` (slice.py header; spec 07 §6, 08 §3) → `art/export/<category>/<name>.png`, and the rect goes into `art/ref/manifests/all.json` (721 entries: sheet, section, x,y,w,h, proposed_name, category, key, thresh). Sliced PNGs are NOT .aseprite sources; if one is edited, the edit lives nowhere reproducible unless it is re-expressed (patch, recolour) in a tools/art/*.py step (derive_busts.py is the pattern).
